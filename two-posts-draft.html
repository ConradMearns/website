Let the Compiler Be Your To-Do List: Programming When You Don't Know What You're Doing

The setup

Most programming advice quietly assumes you already understand the problem you're solving. You're supposed to design first, decompose the system, and then implement the pieces. But in practice — especially on hard or unfamiliar problems — you don't know what you're doing all of the time. That's not a personal failing; it's the normal condition of writing software. The question is whether your workflow takes advantage of that fact or pretends it isn't true.

The failure mode of pretending is familiar: you stall at the top of a file trying to figure out the "right" structure, or you go down a rabbit hole solving a sub-problem you didn't need to solve yet, and the actual goal slips further away.

The approach

The approach is extremely simple: write your programs procedurally when you don't know what you're doing. Start at the top and describe the steps of the solution in the order they happen, as if you were narrating it.

Then, when something starts to get complicated, hand-wave. Don't solve it. Just write a call to a function that doesn't exist yet:

result = parse_declaration(tokens);   // no idea how yet
emit_code(result);                    // also no idea

At that point, your compiler becomes a to-do list. Every "undefined function" error is an item of work you've deferred — explicitly, visibly, and in priority order of whatever you feel ready to tackle next. You never lose track of what's left, because the build won't let you.

And if you want the code to actually run before you've filled everything in, stub the function out: have it return a canned response, a hardcoded value, whatever lets the rest of the program keep moving. Now you can test the parts you do understand while the parts you don't are safely fenced off behind a name.

Why it works

This technique breaks down work as you need it broken down, rather than forcing you to decompose the whole problem upfront. You make progress in a timely manner without having to know how to solve all of your problems before you start. Naming a function you can't write yet is itself a design act — you're defining an interface and deferring the implementation, which is most of what "good architecture" actually is, just done lazily and honestly.

We used this approach back in college to build compilers, shells, and all sorts of complicated C code — code we also had to write by hand, on paper, for our exams. When your "IDE" is a pencil, you learn very quickly that the only way through a big problem is to hand-wave the hard parts into named functions and come back to them. The compiler-as-to-do-list workflow is the same discipline, with better tooling.

Programs Written in English: Solving Big Problems with an LLM, One Conversation at a Time

The setup

There's a false assumption baked into a lot of LLM automation work: that we can come up with the perfect architecture, or the perfect way to solve a problem, on our own and upfront. It's just not realistic — it wasn't realistic before LLMs, and it isn't now.

The symptom of this assumption is reaching, on day one, for LangGraph, complicated harnesses, stacked loops, and the rest of the crazy automation machinery. You end up building infrastructure for a solution you don't understand yet.

The approach

Step 1: Start with a casual chat

The best place to start is a conversation. Set up only the couple of tools you know you will absolutely need — for example, a connection to a database with all of the access and authorization already provided. Then work with your agent (Claude, in my case) in a conversational setting on one particular example of the problem you're trying to automate.

Some ground rules for this session:

  • Interrupt the agent as frequently as you need. If you see it doing something you don't want, stop it and teach it what to do, right there in the session.
  • Don't worry about writing other files or building anything reusable. Just worry about getting this one instance of the task complete.
  • Ask the agent questions. Make sure the agent asks you questions. Treat this as collaborative pair programming and exploration, not delegation.

Step 2: Summarize the session into pseudocode

Once you've completed the goal, distill the session down into a handful of pseudocode lines. Go back through the conversation and pull out:

  • All of the starting input variables,
  • All of the questions that were asked about the problem,
  • All of the nitpicks and corrections you made along the way.

Separate and organize these elements. What you're left with is two things. First, some ground rules — the kind of thing you'd put in a CLAUDE.md, like "use uv over conda." Second, a playbook: a program written in English. Step one, do this. Step two, do this. If this, then that.

Step 3: Run the English program, and revise it

Take the pseudocode to a fresh session and try to solve the same problem again, this time following the playbook. Follow the agent along the way, correct mistakes as before — but now, every correction becomes a revision to the program you're writing in English. You are iterating on a program; the source code just happens to be prose.

Why an English program beats a real one (at this stage)

There are concrete reasons this is more effective than writing actual code first:

  • The interpreter is the LLM. The agent reads an instruction and infers the intent behind it. When it infers the correct intent, you don't need to over-explain yourself or provide more context — the line of pseudocode just works. When it infers the wrong intent and you catch it, you fix the assumption on the spot and build the correct program live. No exiting, no reloading.
  • Nothing mechanical gets in your way. No type inference fighting you, no compiler throwing errors about things you don't care about yet. You work purely in the abstract.
  • Exploration gets cheap — in the way that matters. Yes, it's probabilistic, nondeterministic, and more expensive per run. But the work of exploration — figuring out what the program should even be — becomes far freer.
Just as, back when we wrote programs on paper, you were the interpreter — reading your own handwritten code and executing it in your head — now the agent is the interpreter. The skill transfers directly: write for a reader who fills in reasonable intent, and only specify the parts where intent could plausibly go wrong.

Step 4: From playbook to specification

Keep running the pseudocode program against more examples from your domain — more questions, more inputs. Each run hardens the English. Eventually the pseudocode is robust enough that you can treat it as the specification for a real program.

At that point, open a new session and translate the pseudocode into the coding target of your choice — Python, Rust, whatever fits. Then run the same tests: one example, two, possibly a hundred, and verify them all together. You can even have another coding agent walk through the results and evaluate: did the program's execution match the specification laid out in the pseudocode?

The hard part, moved to day one

By this stage, figuring out how to verify that you've built the right thing becomes the hardest part of the job. And here's the thing: that was always the hardest part of the job. The difference is that instead of arriving at it a month into development — after the architecture is locked in and the sunk costs have piled up — you're working on it from day one.

Notes: things you might want to add

For Post 1 (procedural hand-waving)

  • Name the lineage. This is closely related to "top-down design with stepwise refinement" (Wirth) and to TDD's "fake it till you make it" stubs. Citing the lineage could add credibility for interns — or you may prefer to keep it folksy and skip it.
  • When NOT to use it. A short paragraph on limits: e.g., it works less well when the hard part is a data structure or an invariant rather than a procedure, since you can't hand-wave a representation as easily as a function.
  • A worked micro-example. Ten lines of C or Python showing the main loop of a tiny shell with three undefined functions, then the compiler output acting as the to-do list. Showing the actual error list makes the metaphor land.
  • Stubs vs. TODOs. Why is a missing function better than a // TODO comment? Worth one sentence: comments are ignorable; link errors aren't.

For Post 2 (programs in English)

  • An example playbook. Even 6–8 lines of real pseudocode from one of your sessions (sanitized) would make this concrete. Right now the reader has to imagine what the artifact looks like.
  • How you "interrupt and teach." Interns may not know what correcting an agent mid-task actually looks like. One short before/after exchange would help.
  • Version control for the English program. Do you keep the playbook in git? How do you track revisions across sessions? Worth a sentence even if the answer is "a markdown file."
  • When to stop iterating in English. What's the signal that the pseudocode is "robust enough" to become a spec? Number of clean runs? No new nitpicks for N examples? Right now that judgment call is implicit.
  • Cost framing. You concede LLM runs are more expensive — you could flip this into the argument that exploration in English is still cheaper than a month of building the wrong harness.
  • The verification story deserves more. Your closing point (verification moved to day one) is the strongest idea in the piece, and it lands in two sentences. Consider expanding: what does the verifying agent actually check? Spec line by spec line? Do you keep a table of example inputs and expected outcomes?
  • Tie the two posts together. They share a thesis: defer what you don't understand behind a name (a function, a line of pseudocode) and let an interpreter (compiler, you on paper, the agent) tell you what's left. A closing paragraph in Post 2 referencing Post 1 would make them feel like a pair — useful since the same audience reads both.
