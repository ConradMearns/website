Let the Compiler Be Your To-Do List: Programming When You Don't Know What You're Doing

The setup

This is a general style of programming, without large language models, which specifically takes advantage of the fact that we don't know what we're doing all of the time. Most programming advice quietly assumes the opposite: that you can design first, decompose the system, and then implement the pieces. But on hard or unfamiliar problems, not knowing is the normal condition of writing software. The question is whether your workflow takes advantage of that fact or pretends it isn't true.

The failure mode of pretending is familiar: you stall at the top of a file trying to figure out the "right" structure, or you go down a rabbit hole solving a sub-problem you didn't need to solve yet, and the actual goal slips further away.

The approach

The approach is extremely simple. The general approach is just: write programs procedurally when you don't know what you're doing. Start at the top and describe the steps of the solution in the order they happen, as if you were narrating it.

When something starts to get complicated, you can hand-wave a lot by just writing a call to a function that doesn't exist yet:

result = parse_declaration(tokens);   // no idea how yet
emit_code(result);                    // also no idea

Your compiler, at that point, will basically act as a to-do list for you. Every "undefined function" error is an item of work you've deferred — explicitly, visibly, and in whatever priority order you feel ready to tackle next. You never lose track of what's left, because the build won't let you.

And if you want code to run — if you want to skip over one of these procedural functions you've written — you could have it return a canned response or whatever. Now you can test the parts you do understand while the parts you don't are safely fenced off behind a name.

Why it works

This was a very effective technique of breaking down work as you needed, so that you could accomplish your goals in a timely manner without having to know how to solve all of your problems upfront. Naming a function you can't write yet is itself a design act — you're defining an interface and deferring the implementation, which is most of what "good architecture" actually is, just done lazily and honestly.

This is an approach that we used back in college, specifically to build compilers, shells, all sorts of complicated C code that we also had to write by hand on paper for our exams. When your "IDE" is a pencil, you learn very quickly that the only way through a big problem is to hand-wave the hard parts into named functions and come back to them. The compiler-as-to-do-list workflow is the same discipline, with better tooling.

Programs Written in English: Solving Big Problems with an LLM, One Conversation at a Time

The setup

This post is about using large language models to write and solve large problems. The main idea here is that we want to avoid this false assumption that we can just come up with the perfect architecture or the perfect way to solve a problem on our own, because it's just not realistic.

So, instead of looking towards solutions like LangGraph, or complicated harnesses, or stacked loops, or all of this other crazy automation bullshit — start somewhere much smaller.

Step 1: Start with a casual chat

The best place to start is just with a casual chat. Come up with a couple tools that you know you will absolutely need to have, such as a connection to a database that has all of the access and authorization already provided. And then just work with your agent, like Claude, in a conversational setting to try to solve one particular problem, or example problem, that you are trying to automate.

Some ground rules for this session:

  • Work through the problem. Interrupt the agent as frequently as you need — if you see it doing something you don't want it to do, interrupt it, and teach it what to do in this session.
  • Don't worry about writing other files. Just worry about getting the one instance of the task complete.
  • Ask Claude questions. Make sure that Claude asks you questions, and treat this as a collaborative pair programming exercise and exploration.

Step 2: Summarize that session into pseudocode

Once you've completed that goal, you can summarize that session into a handful of pseudocode lines. The idea would be: figure out what all of the starting input variables were, all of the questions that were asked related to the problem, all of the nitpicks — and separate and organize these elements so that what you're left with is some ground rules, kind of like what you would put in a CLAUDE.md, like "use uv over conda."

And then you have a playbook. And this playbook, or pseudocode, is basically a program written in English. Step one, do this. Step two, do this. If this, then that.

Step 3: Run the English program, and revise it

Take the pseudocode to a new session and try to solve the same problem. Again, follow Claude along the way, correct mistakes. And through this process, revise the program that you've been making in English. You are iterating on a program; the source code just happens to be prose.

Why an English program beats a real one (at this stage)

There are some concrete reasons why this is more effective than writing a program.

  • For one, the interpreter is the large language model. The interpreter is the agent. Claude can read in an instruction and assume what the correct intent is. And the nice thing is that if Claude assumes the correct intention, then you don't need to overexplain yourself. You don't need to provide any more context. If Claude reads an intention and gets it wrong, and you catch that, you have the opportunity to fix that assumption, fix that intent, and build the correct program live. You don't have to exit or reload anything.
  • You don't have to worry about type inferencing getting in your way. You don't have to worry about the compiler throwing errors that you maybe don't necessarily care about yet. You can work purely in the abstract.
  • Even though it is probabilistic and nondeterministic and more expensive, you're able to do the work of exploration a lot more freely.
Just as on paper, you are the interpreter — now Claude is the interpreter. The skill transfers directly: write for a reader who fills in reasonable intent, and only specify the parts where intent could plausibly go wrong.

Step 4: From playbook to specifications for a real program

Once you've gone through this systematic approach of working out a pseudocode program with your agent, you can start using that pseudocode program on more examples from your domain — more questions, for instance. Then you can take that pseudocode, which is robust enough English, and you can treat that as specifications for a real program.

At that point, you can have a new session and try to translate that pseudocode into a coding target of your choice, like Python or Rust. Once you have that code translated to Python or Rust, again, you want to do the same tests. You want to run through one, two, possibly a hundred example inputs, and then verify them altogether. And you could have another coding agent walk through and evaluate: did the program execute to match the specifications of the pseudocode?

The hard part, moved to day one

At this point, trying to figure out how you verify you've built the right thing becomes the hardest part of this job. And I would add that this was always the hard part of the job. But now, instead of getting to this hard part a month into development, you're working on it on day one.
